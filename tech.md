## 1. Проект

Auteko Workplace — информационная система для небольшого торгового бизнеса: учёт номенклатуры (товары-двигатели), партий поставки, сделок реализации, покупателей и остатков на складе. Один пользователь или небольшая команда входит по паролю, ведёт каталог и партии, фиксирует сделки (даты договора, спецификации, оплаты, УПД), следит за остатками по подсвеченным порогам и выгружает реестр реализации и остатки в Excel. Данные хранятся в PostgreSQL. Пользователь — сотрудник компании; интерфейс на русском языке.

Цель: готовый продукт для постоянной работы, а не демо. Не цели: многопользовательские роли и права (кроме защиты входа), мультиязычность, публичная витрина, мобильное приложение, интеграции с 1С/обменами.

Список функций:

1. Вход по email и паролю, выход с отзывом сессий.
2. Справочник номенклатуры с импортом из Excel.
3. Партии поставки с себестоимостью по курсу юаня.
4. Сделки реализации с контролем остатков, переходами статусов и экспортом реестра.
5. Справочник покупателей (контрагентов).
6. Остатки склада с порогами «зелёный/жёлтый/красный» и экспортом.
7. Настройки компании и нумерации, загрузка курса CNY с сайта ЦБ РФ.
8. Экспорт списков в xlsx.

Окружение и доверие: система работает на VPS под Node.js за nginx/Caddy с TLS, слушает 127.0.0.1; доступ только внутри компании по аутентификации. Хранит персональные данные контактов и коммерческие цены. Угрозы: шифрованный канал обеспечивает прокси; приложение защищает сессии, формы и запросы (раздел 18). Вне модели: физический доступ к диску VPS, TLS-конфигурация прокси.

Нефункциональные требования:

| требование           | значение                                                                            |
| -------------------- | ----------------------------------------------------------------------------------- |
| объём данных         | 10000 позиций и 50000 сделок без деградации (импорт ограничен 5000 строк за раз)     |
| время отклика        | список через API за 500 мс при 10000 записей на сервере VPS                          |
| параллелизм          | 10 одновременных запросов без ошибок (пул PostgreSQL max 10)                        |
| платформы и браузеры | Node.js 20 LTS; браузеры актуальных версий Chromium, Firefox, WebKit                |
| доступность сервиса  | сбой PostgreSQL: ошибка 5xx без паники процесса, рестарт PM2 восстанавливает работу |
| обновление           | с предыдущей версии; миграции применяются только вперёд                             |
| резервная копия      | `pg_dump` по расписанию вне приложения (README), восстановление проверяется         |
| наблюдаемость        | журнал stdout, проверка готовности, версия приложения                               |

## 4. Контракт данных (заморожен)

Идентификаторы всех сущностей: UUID, наружу строкой. Стиль имён полей: `snake_case` в хранилище, совпадает в типах приложения (раздел 5 API возвращает `snake_case`-ключи). Полные типы — `src/types/index.ts`.

Перечисления: `status` продукта = `active|archived`; статус сделки `DealStatus` = `new|confirmed|shipped|done|cancelled`; статус остатка = `green|yellow|red`.

Сущность `users`:

| поле            | тип          | ограничения                                   |
| --------------- | ------------ | --------------------------------------------- |
| `id`            | uuid pk      |                                               |

Сущность `products`:

| поле                     | тип                      | ограничения                          |
| ------------------------ | ------------------------ | ------------------------------------ |
| `id`                     | uuid pk                  |                                      |
| `auteko_article`         | text unique              | уникальность после миграции 001      |
| `original_articles`      | text[]                   |                                      |

Сущность `batches` (партия): `id` uuid, `batch_number` text unique (формат `P-001`, миграция 001 даёт UNIQUE), `product_id` → products, `quantity` int, `price_exw_cny` numeric, `cny_rate` numeric, `cny_rate_date` date, `customs_duty_pct`, `transport_cost`, `other_costs`, расчётные `cost_price_rub`, `markup_coefficient`, `price_kp_rub`, `profit_per_unit` (считает триггер БД), `gtd_number`, `gtd_date` (nullable), `created_at`/`updated_at`.

Сущность `deals` (сделка): `id` uuid, `deal_number` text unique (формат `R-001`), `client_id` → clients, `product_id`, `batch_id` → batches, `contract_number`, `spec_number` (nullable), `quantity` int, `price_with_vat`, `total_amount` (авто = quantity × price), `delivery_deadline`, `prepayment_date`, `actual_delivery_date`, `actual_payment_date`, `upd_number`, `upd_date` (nullable), `status`, `notes` (nullable), `created_at`/`updated_at`.

Сущность `clients` (покупатель): `id` uuid, `company_name` text, `inn`, `contact_person`, `phone`, `email`, `notes` (nullable), `created_at`/`updated_at`.

Сущность `settings` (настройка ключ-значение): `key` varchar(100) pk, `value` text not null, `updated_at` timestamptz. Ключи по умолчанию: `stock_threshold_yellow=5`, `stock_threshold_red=1`, `default_markup=1.25`, `batch_number_prefix=P`, `deal_number_prefix=R`, `deal_counter`, `batch_counter`, `company_name`, `company_inn`, `company_address`.

Объекты БД: представление `stock_balance` (остаток по позиции: количество партии минус сумма незавершённых сделок, статус green/yellow/red по товарным или общим порогам), функция `next_number(prefix_key, counter_key)` (возвращает номер вида `префикс-NNN` с ведущими нулями до 3 цифр и инкрементирует счётчик внутри одной функции).

Примечание (задача слайса 0B): базовая DDL-схема (`users`, `products`, `batches`, `clients`, `deals`) и триггер расчёта партии в репозитории отсутствуют, а README ссылается на отсутствующий файл `auteko_schema.sql`. Слайс 0B собирает `db/schema.sql`, фиксирующий фактическую структуру, и заменяет ссылку в README.

Правила, действующие в любом проекте:

- Время хранится в UTC (`timestamptz`). Наружу отдаётся как ISO 8601. Даты без времени в типе приложения — строка `YYYY-MM-DD`, проверяется `dateStr` (валидация календарной даты).
- Булевы и перечисления на границе слоя данных переводятся в типы приложения одну функцию-маппер.
- Версия схемы хранится в хранилище через миграции. Изменение схемы — новая миграция, существующую миграцию не правят. Хранилище новее приложения не открывается.
- Идентификаторы UUID не переиспользуются после удаления. Наружу id приходит строкой и разбирается по разделу 8.
- Поля и сущности, которых здесь нет, добавляются только через `CONTRACT GAP`.

## 5. API доступа к данным (заморожен)

`src/lib/db.ts` экспортирует только это:

```
query<T>(text: string, params?: readonly unknown[]): Promise<T[]>
queryOne<T>(text: string, params?: readonly unknown[]): Promise<T | null>
withTransaction<T>(fn: (client: PoolClient) => Promise<T>): Promise<T>
```

Правила:

- Функции принимают уже валидные данные. Валидацию делает слой выше (zod-схемы в обработчиках).
- Ожидаемое отсутствие (`queryOne` не нашёл строку) — `null` без исключения. Изменение несуществующей сущности ничего не создаёт.
- Все запросы параметризованы ($1, $2, ...). Конкатенация данных в SQL запрещена; для `LIKE` метасимволы (`%`, `_`, `\`) экранирует `escapeLike`.
- Операция из нескольких запросов идёт в одной транзакции (`withTransaction` на одного клиента: BEGIN/COMMIT/ROLLBACK).
- Пул создаётся один раз (в dev переживает hot-reload через `globalThis`), `max: 10`, адрес из `DATABASE_URL`.
- Имена функций блокировки и переходов: `lockBatchStock(client, batchId, excludeDealId?)` — `SELECT ... FOR UPDATE` плюс сумма незавершённых сделок; `canTransition(from, to)` — карта допустимых переходов статуса сделки. Вызываются только внутри `withTransaction`.
- Тесты получают отдельную временную базу (создаётся и стирается в setup/teardown, план 0B), реальные данные не трогают.

## 6. Интерфейс

Продукт имеет UI (веб-админка, русский язык). Компоненты лежат в `src/components/` и используются во всех слайсах: свой аналог вместо существующего компонента не пишется.

| компонент    | текст/пропсы                                             | назначение                                        |
| ------------ | -------------------------------------------------------- | ------------------------------------------------- |
| `Sidebar`    | без пропсов; массив `NAV`, выход через POST `/api/auth/logout` | навигация слева, текущий раздел подсвечен `aria-current` |
| `MobileNav`  | без пропсов; те же 6 пунктов                              | фиксированная нижняя панель для ширины ≤ 768 px    |
| `Tooltip`    | `text`, `label?`, `children?`                            | подсказка через портал, доступная с клавиатуры     |

Формы создания и редактирования лежат прямо внутри страниц `(app)/*/page.tsx` (клиентские компоненты) и обращаются к API; ответ приходит в формате `ApiResponse<T>`. Выделенный каталог `components/forms/` не создаётся.

Требования ко всем страницам:

- Заголовки и строки интерфейса — русские (продукт одноязычный; раздел 17).
- Поля ввода снабжены подписью, при ошибке отмечаются ошибкой и текстом ошибки.
- Тексты при ошибках формы возвращаются в удобном виде `ApiResponse.error` без обрезки введённого.
- Разрушительные действия (архив, отмена сделки) требуют подтверждения запросом и работают без JS (обычные формы post).

## 7. Точки входа (маршруты)

Страницы (защищены `middleware.ts`: без валидного JWT редирект на `/login`; `/` → перенаправление на `/products`):

| путь                  | что делает                                                            |
| --------------------- | --------------------------------------------------------------------- |
| `/login`              | страница входа                                                        |
| `/products`           | справочник номенклатуры: поиск, фильтры, создание, правка, импорт xlsx |
| `/batches`            | партии с расчётом себестоимости                                       |
| `/deals`              | сделки: реестр, переходы статусов, экспорт                            |
| `/clients`            | покупатели                                                            |
| `/stock`              | остатки и пороги                                                      |
| `/settings`           | настройки компании, порог, нумерации                                  |

API (каждый обработчик дополнительно к middleware сам проверяет сессию: 401 при её отсутствии):

| путь                       | методы                  | что делает                                                                                          |
| -------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------- |
| `api/auth/login`           | POST                    | bcrypt-сверка, ограничение попыток, фиктивный хеш (ровный тайминг) при отсутствии email, создание cookie сессии |
| `api/auth/logout`          | POST                    | `token_version++` (отзыв всех сессий) и удаление cookie                                              |
| `api/products`             | GET, POST               | список с пагинацией/поиском/фильтрами; создание                                                       |
| `api/products/[id]`        | GET, PUT, DELETE        | чтение; частичное обновление; `DELETE` = архивация (`status=archived`), запрещена при партиях           |
| `api/products/import`      | GET, POST               | GET отдаёт шаблон xlsx; POST импортирует файл                                                          |
| `api/batches`              | GET, POST               | список с данными товара; создание                                                       |
| `api/batches/[id]`         | GET, PUT, DELETE        | чтение; обновление в транзакции (`lockBatchStock`); удаление запрещено при активных сделках             |
| `api/deals`                | GET, POST               | список с соединениями клиента/партии, фильтры по статусу и overdue; создание с проверкой остатка        |
| `api/deals/[id]`           | GET, PUT, DELETE        | чтение; обновление с контролем переходов `canTransition` и пересчётом остатка; `DELETE` = отмена, запрещена для `done` |
| `api/deals/export`         | GET                     | xlsx «Реестр реализации»                                                                               |
| `api/clients`              | GET, POST               | список со счётчиком сделок; создание                                                                  |
| `api/clients/[id]`         | GET, PUT, DELETE        | чтение; обновление; удаление запрещено при активных сделках                                            |
| `api/stock`                | GET                     | остатки из `stock_balance` + сводка (счётчики статусов, стоимость остатка)                             |
| `api/stock/export`         | GET                     | xlsx остатков                                                                                          |
| `api/settings`             | GET, PUT                | чтение всех настроек одним объектом; поштучный upsert каждого ключа                                    |
| `api/settings/cny-rate`    | GET                     | курс CNY с сайта ЦБ РФ (XML), кэш 1 ч, 503 при недоступности источника                                 |
| `api/settings/next-number` | GET, POST               | GET предпросмотр следующего номера (без инкремента); POST вызывает `next_number()`                     |

Правила:

- Изменяющие операции выполняются только не безопасными методами (POST/PUT/DELETE). GET ничего не меняет.
- Действие принимает целевое состояние (`status: archived`), повторная отправка даёт тот же результат.
- Ошибка валидации — 400 с кодом ошибки и введёнными данными. Несуществующий UUID — 404; неразобранный `badId` — 400 (409 при конфликте UNIQUE: 23505).
- Пагинация: `limit` (по умолчанию 50, максимум 200), `page`; параметр дважды — берётся первое значение.
- Защита от межсайтовых запросов встроена в `middleware.ts`: для мутаций Origin обязан совпадать с origin запроса или `NEXT_PUBLIC_APP_URL`, иначе 403; встроенная защита Next не отключается; cookie `auteko_session` — `HttpOnly`, `Secure` (в проде), `SameSite=Lax`.

## 8. Валидация

`src/lib/validation.ts` (чистые функции) плюс zod-схемы в обработчиках:

```
badId(raw: string): boolean — возвращает true, если raw не UUID (правило ^[0-9a-f]{8}-[0-9a-f]{4}-...)
dateStr(v: unknown): boolean — непустая строка-календарная дата (2026-02-30 отклоняется)
escapeLike(s: string): string — экранирует %, _, \ для ILIKE
parseLimit(v: unknown, def = 50): number, максимум 200
parsePage(v: unknown): number, начиная с 1
zodDetails(e: ZodError): ошибку без схемных подробностей в проде
```

Лимиты полей фиксируются zod-схемами в конкретных обработчиках (каждая обязательная строка имеет максимум; неограниченных полей нет). Тексты ошибок собирает обработчик на русском языке.

Правила:

- Ошибки возвращаются агрегированно в `ApiResponse.error`, без обрезки введённых данных.
- Не-строка на входе текстового поля: обязательное поле даёт ошибку «обязательно», необязательное становится пустой строкой/null.
- `\r\n` в тексте нормализуется в `\n` до подсчёта длины и до сохранения.
- Краевые пробелы обрезаются у заголовков, имён, артикулов; у примечаний сохраняются.
- `badId` принимает только канонический UUID; всё иное — 400 в чтении и в каждом изменяющем действии.
- Проверка атрибутами разметки (`maxLength`) серверную проверку не заменяет.
- Импорт Excel: файл ≤ 5 МБ, ≤ 5000 строк, ZIP-подпись проверяется ещё до парсинга, каждая строка прогоняется через zod-схему; строки с дубликатами артикулов пропускаются (NOT EXISTS).

## 9. Тесты

Состояние: **тестов нет**, вся инфраструктура проверок — предмет слайса 0B. Ниже — контракт, по которому они строятся.

Принципы:

1. Тесты выводятся из критериев приёмки раздела 15, а не из готового кода. ID критерия `S<метка>.<номер>` входит в название теста: `S1.2: rejects blank article and writes nothing`. Пометки `(ручной)`, `(CI: job)` означает проверку человеком или job'ом CI.
2. Красный тест чинится правкой кода. Тесты не удаляются, не ослабляются и не пропускаются (`skip`, `only`, `todo` запрещены линтером).
3. Баг, найденный ревью или руками: сначала падающий тест `BUG-<n>`, потом правка. Тест остаётся навсегда.
4. Запрещённый вид теста: «сохранили и проверили, что сохранилось». На каждый критерий с отказом есть тест на отказ.
5. Названия тестов, переменные и комментарии английские (раздел 11).

Уровень, размещение и запуск — как в таблице:

| уровень     | где                  | что проверяет                                                          | запуск         |
| ----------- | -------------------- | ----------------------------------------------------------------------- | -------------- |
| unit        | `tests/`             | чистые модули: `validation.ts`, `stock.ts` (карта переходов), `xlsx.ts`  | `gate`         |
| integration | `tests/`             | обработчики API на изолированной базе, скрипты                          | `gate`         |
| e2e         | `e2e/`               | собранное приложение: сценарии, без JS, заголовки, доступность           | CI, `gate-full`|
| load        | `e2e/` или `scripts/`| бюджет 10000 записей и 10 одновременных запросов (слайс E)              | CI             |
| mutation    | `mut`                | качество тестов чистых модулей, порог 80%                               | CI             |

Изоляция: `DATABASE_URL` в тестах указывает на временную базу, создаётся и стирается в setup/teardown; реальные данные не трогаются. Хелперы `tests/helpers` (фабрика запросов `nextRequest(path, init)` и извлечения cookie) пишутся в 0B.

Обязательные инварианты:

- `escapeLike` делает спецсимволы (`%`, `_`, `\`) безопасными в шаблоне ILIKE; поисковый запрос обрабатывается буквально.
- `canTransition` не принимает недопустимый переход ни при каких парах, отмена `done` запрещена.
- `validate` (zod-схемы): при успехе обязательные поля непустые и в пределах лимита; при ошибке названная причина.
- `parseLimit/parsePage` возвращают значения по умолчанию, а не ложные числа, на всех нечисловых входах.
- `readFirstSheet` на файле больше лимита выдаёт код `too_many`, не падает.

Покрытие (после 0B): 100% строк/ветвей для чистых модулей (`validation`, `stock`, `xlsx`, `rate-limit`), ≥ 90% для остального. Мутации: порог 80% на чистых модулях.

## 11. Конвенция текста

Интерфейс по факту на русском; тесты, комментарии, названия переменных, сообщения журнала — английские. Коммиты — Conventional Commits фиксированного формата:

```
type(scope): summary
```

- `type` из набора `feat|fix|test|refactor|chore|docs`;
- `scope`: строчные латинские буквы, цифры и дефис;
- `summary` в императиве, со строчной буквы, без точки, до 50 символов;
- тело только чтобы объяснить _почему_; коммитить маленькими шагами, каждый коммит по возможности проходит `types`.

Примеры: `feat(deals): enforce status transitions`, `test(validation): cover escapeLike`.

Правила прозы: активный залог, конкретика, без вводных оборотов и наречий-усилителей. Закомментированный код не оставляется. Официальные документы (CHANGELOG, SECURITY, CONTRIBUTING) — английские, README — русский; переводов не планируется.

## 18. Безопасность

Модель угроз. Защищаем: коммерческие данные (цены, сделки, остатки), персональные данные контактов, сессии сотрудников, секреты (`JWT_SECRET`). Атакующий: любой пользователь интернета без валидной сессии; возможны перебор входа и межсайтовые запросы. Вне модели: физический доступ к VPS, конфигурация TLS у прокси, уязвимости хостинга.

| угроза                            | мера                                                                                        | где        |
| --------------------------------- | --------------------------------------------------------------------------------------------- | ---------- |
| Доступ без аутентификации         | JWT-сессия в HttpOnly cookie; middleware + повторная проверка в каждом обработчике (401)       | S7 (вып.)  |
| Перебор пароля                    | 5 попыток/15 мин, одинаковый ответ и фиктивный хеш (ровный тайминг), пароль ≥ 12 символов, установлен только скриптом | S7 (вып.)  |
| Компромисс сессии                 | HS256 JWT, срок 12 ч, `Secure`/`HttpOnly`/`SameSite=Lax`, отзыв через `token_version`          | S7 (вып.)  |
| CSRF                              | проверка Origin в middleware для мутаций; встроенная защита Next не отключается               | S7 (вып.)  |
| Инъекция в SQL                    | параметризованные запросы `$n`, `escapeLike` для ILIKE; конкатенации нет                       | ревью      |
| XSS                               | вывод через механизм шаблонов React; `dangerouslySetInnerHTML` не используется                  | ревью      |
| Clickjacking, sniffing, Referer   | заголовки ниже в `next.config.js`                                                              | 0A (вып.)  |
| Инъекция формул в Excel           | `sanitizeCell`, пользовательский ввод не попадает в формулы                                   | S1 (вып.)  |
| Извлечение секретов               | только из окружения; `JWT_SECRET` ≥ 32, проверка при старте; `.env.local` в `.gitignore`       | S7 (вып.)  |
| Секреты в репозитории             | `secrets` в CI (план 0B), история чистая                                                       | CI         |
| Уязвимые зависимости              | `audit` в CI и по расписанию (план 0B)                                                          | CI         |
| Утечка внутренностей в ошибках    | `zodDetails` скрывает детали схемы в проде; коды 400/404 вместо 500                             | 0A (вып.)  |
| Излишние права БД                 | роль `auteko_app` без DDL и суперпользователя                                                  | S7 (вып.)  |
| Утечка данных в журнале и ошибках | пользовательские данные и секреты не попадают в заголовки, журнал и сообщения об ошибках        | ревью      |

Заголовки (выставляет `next.config.js`, HSTS добавляет прокси):

```
Content-Security-Policy: default-src 'self'; frame-ancestors 'none'
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: no-referrer
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=()
```

`poweredByHeader: false`. `NEXT_PUBLIC_APP_URL` участвует в проверке Origin и в решении о `Secure` cookie: в проде схема `https`.

Нет функции `safeRedirect`: интерфейс не использует адресов возврата из параметров — пользователь после входа всегда попадает в `/products`. Введение обратных адресов (`redirectTo`) допускается только через `safeRedirect` и `CONTRACT GAP`.
